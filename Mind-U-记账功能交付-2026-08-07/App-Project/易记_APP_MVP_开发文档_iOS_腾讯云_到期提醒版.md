# 易记 APP – 早期最低成本版本开发文档（iOS + 腾讯云 Web 服务器）

**项目名称**：易记  
**平台**：iOS + 腾讯云 Web 服务器  
**版本**：v0.1 MVP  
**更新日期**：2026-06-05  

---

## 1. 项目概述

易记是一款帮助用户快速记录“物品位置、生活事项、提醒事项”的个人生活记忆 APP。

用户可以通过语音或文字输入一句自然语言，例如：

> 我把户口本放在红抽屉最上面。

系统将自动保存这条记录，并在用户未来查询时返回：

> 你在 2026 年 6 月 5 日记录过：户口本放在红抽屉最上面。

MVP 阶段重点不是复杂 AI，而是低成本、稳定、可用地完成：

- 快速记录
- 自动解析
- 历史找回
- 简单提醒

---

## 2. 产品目标（MVP）

### 2.1 核心目标

1. 用户可以用一句话快速记录生活中的重要信息。
2. 系统自动识别物品、位置、时间、类型等关键信息。
3. 用户可以通过自然语言或关键词快速找回过去记录。
4. 早期版本尽量不依赖付费 AI 模型，降低成本。
5. 服务器使用现有腾讯云 Web 服务器，主要承担 API、数据库和业务逻辑。

### 2.2 核心价值

- **快速记录**：想到什么立刻说一句，不需要手动选择类别、日期、时间。
- **可靠找回**：未来通过关键词或自然语言找到历史记录。
- **低成本上线**：iOS 本地语音识别 + Web 服务器规则解析 + 数据库存储。
- **后期可扩展**：未来可接入大模型、向量搜索、图片识别、自动提醒等能力。

## 3. MVP 功能范围

### 3.1 支持功能

| 功能 | 说明 |
|---|---|
| 语音输入 | 使用 iOS 系统语音识别，将语音转文字 |
| 文字输入 | 用户可手动输入记录内容 |
| 自动解析 | 基于规则识别物品、位置、时间、类型 |
| 记录保存 | 将原始文本和结构化信息保存到数据库 |
| 历史查询 | 支持关键词查询历史记录 |
| 模板化回答 | 将查询结果整理成自然语言返回 |
| 时间线 | 按时间顺序展示历史记录 |
| 简单分类 | 物品位置、日程提醒、想法笔记、其他 |
| 可选提醒 | 对带有未来时间的记录创建提醒 |

### 3.2 暂不支持功能

| 功能 | 原因 |
|---|---|
| 大模型深度理解 | MVP 阶段控制成本 |
| 图片识别 | 后续版本扩展 |
| 多端同步 | 先聚焦 iOS |
| Android / Web 端 | 后续版本扩展 |
| 复杂自然语言推理 | 先用规则和关键词满足核心场景 |
| 本地部署语音模型 | 普通 Web 服务器不适合跑重模型 |

### 3.3 当前阶段产品限制说明

1. 当前 iOS MVP 阶段对本地记录数量设置上限，单用户最多可保存 `30` 条记录。
2. 当记录数量达到 `30` 条后，客户端将阻止继续新增记录。
3. 该限制当前仅作为产品阶段性约束使用，先不开发付费购买、订阅、恢复购买等能力。
4. 后续如进入商业化阶段，再补充升级页、StoreKit 支付链路和权益校验逻辑。

## 5. 技术选型

| 模块 | 技术方案 | 说明 |
|---|---|---|
| iOS 开发 | Swift + SwiftUI | 原生开发，体验好，迭代快 |

## 6. iOS 客户端设计

### 6.1 主要页面

| 页面 | 功能 |
|---|---|
| 首页 | 展示最近记录，提供快速录入入口 |
| 录入页 | 语音按钮、文字输入框、确认保存 |

| 设置页 | 登录信息、隐私设置、提醒开关 |

### 6.2 语音识别流程

1. 请求麦克风权限。
2. 请求语音识别权限。
3. 用户点击或长按语音按钮。
4. iOS 使用 `SFSpeechRecognizer` 将语音转文字。
5. 用户确认识别文本。
6. App 将文本发送到服务器。

### 6.3 iOS 请求示例

```json
POST /api/v1/records

{
  "user_id": 123,
  "content": "我把户口本放在红抽屉最上面",
  "source": "voice",
  "client_created_at": "2026-06-05 10:30:00"
}
```

```sql
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
```

```sql
  extra JSON COMMENT '扩展字段',

  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_user_created (user_id, created_at),
  INDEX idx_user_object (user_id, object_name),
  FULLTEXT INDEX idx_content (content)
);
```

## 9. 规则解析设计

### 9.1 解析目标

从用户输入文本中提取：

- 物品
- 位置
- 时间
- 类型
- 标签
- 是否需要提醒

### 9.2 物品位置解析规则

| 用户表达 | 解析结果 |
|---|---|
| 我把户口本放在红抽屉最上面 | object_name=户口本，location=红抽屉最上面 |
| 身份证在床头柜第二层 | object_name=身份证，location=床头柜第二层 |
| 钥匙放门口鞋柜上 | object_name=钥匙，location=门口鞋柜上 |
| 银行卡收在书房文件夹里 | object_name=银行卡，location=书房文件夹里 |

### 9.3 正则规则示例

```text
我把(.+?)放在(.+)
(.+?)放在(.+)
(.+?)在(.+)
(.+?)收在(.+)
(.+?)藏在(.+)
(.+?)放到(.+)
```

### 9.4 时间解析规则

| 用户表达 | 解析结果 |
|---|---|
| 今天 | 当前日期 |
| 明天 | 当前日期 + 1 天 |
| 后天 | 当前日期 + 2 天 |
| 下周三 | 下一个周三 |
| 明天下午三点 | 明天 15:00 |
| 每月 5 号 | 周期性提醒 |

### 9.5 分类规则

| 分类 | 关键词 |
|---|---|
| 物品位置 | 放在、在、收在、藏在、放到、搁在 |
| 日程提醒 | 提醒我、明天、下周、几点、到时候 |
| 想法笔记 | 想法、灵感、记一下、备忘 |
| 财务 | 银行卡、信用卡、账单、报销、发票 |
| 证件 | 身份证、户口本、护照、驾驶证 |
| 健康 | 药、体检、复诊、医院 |
| 购物 | 买、快递、购物、下单 |

## 10. 查询逻辑

### 10.1 MVP 查询方式

MVP 阶段采用：

1. 关键词搜索
2. 按时间倒序排序
3. 返回最近 3~5 条记录
4. 模板化组织答案

### 10.2 SQL 示例

```sql
SELECT *
FROM records
WHERE user_id = 123
  AND (
    content LIKE '%户口本%'
    OR object_name LIKE '%户口本%'
    OR location LIKE '%户口本%'
  )
ORDER BY record_time DESC, created_at DESC
LIMIT 5;
```

### 10.3 返回模板

**单条结果**

```text
你在 2026 年 6 月 5 日记录过：户口本放在红抽屉最上面。
```

**多条结果**

```text
我找到了 3 条相关记录：

1. 2026 年 6 月 5 日：户口本放在红抽屉最上面。
2. 2025 年 12 月 20 日：户口本放在书房文件柜。
3. 2025 年 3 月 8 日：户口本复印件放在蓝色文件夹。
```

**无结果**

```text
暂时没有找到“户口本”的相关记录。你可以换个关键词，比如“证件”“红抽屉”“文件夹”再试试。
```

## 12. 市场情况与可行性分析（产品经理视角）

### 12.1 市场结论

从当前类似产品来看，“语音输入 + 自动识别时间 + 创建提醒/日程”已经不是全新的功能。Apple Reminders、滴答清单、Todoist、Fantastical、Google Gemini 等产品都已经覆盖了部分能力。

因此，易记不建议定位为：

> 又一个待办事项 APP  
> 又一个日历提醒 APP  
> 又一个语音备忘录 APP

更合理的定位是：

> 面向个人生活场景的“长期记忆找回工具”，帮助用户记录“东西放在哪里、什么时候做过什么、未来怎么找回来”。

这个定位与普通提醒工具有明显区别。传统提醒类产品主要解决“未来不要忘”，易记要解决的是：

> 过去发生过，但用户现在忘了，需要被找回。

例如：

- 我把户口本放在哪里了？
- 上次身份证复印件放哪了？
- 那张发票我什么时候收到的？
- 孩子的疫苗本放在哪个柜子？
- 去年办房子那份材料放哪里了？

这类场景不是典型日历、待办、笔记产品的核心能力，存在差异化机会。

---

### 12.2 类似产品与竞品情况

#### 12.2.1 Apple Reminders / Siri

Apple Reminders 已支持通过 Siri 语音创建提醒，并支持自然语言输入来创建提醒设置。Apple Intelligence 还可以根据其他 App 中的文本建议提醒，并自动分类提醒事项。

**对易记的影响：**

Apple 系统级能力会覆盖一部分“语音创建提醒”的需求，因此易记不应该把“语音提醒”作为唯一卖点。否则很容易被系统自带功能替代。

**易记的差异化机会：**

Apple Reminders 更偏“任务和提醒”，不是围绕“长期生活记忆检索”设计。易记可以强化物品位置、生活事件、家庭资料、证件材料等低频但重要的信息找回。

---

#### 12.2.2 滴答清单

滴答清单支持文本创建、语音输入、Siri 添加任务，并可以智能识别日期和时间，为任务设置提醒。其功能较完整，覆盖待办、日程、番茄钟、习惯、协作等。

**对易记的影响：**

滴答清单已经很好地满足了“任务管理 + 时间提醒”需求。易记如果直接做任务清单，会进入成熟红海市场。

**易记的差异化机会：**

滴答清单的核心是任务管理，而不是“生活物品和过去记录的记忆库”。易记可以避免复杂 GTD 和项目管理，专注在更轻量的“一句话记录 + 未来找回”。

---

#### 12.2.3 Todoist

Todoist 支持自然语言创建提醒，用户可以通过输入日期和时间表达快速创建任务和提醒。

**对易记的影响：**

自然语言任务创建已经是成熟效率工具的常见能力，单纯做日期识别和提醒设置，竞争力不足。

**易记的差异化机会：**

Todoist 面向任务和生产力管理，用户需要主动维护项目、标签、优先级等。易记可以反其道而行之，主打“无整理负担”，用户只说一句话，系统保存原文和关键字段，未来能搜回来即可。

---

#### 12.2.4 Fantastical

Fantastical 主打自然语言日历输入，是日历类产品中的典型代表。用户可以用自然语言快速创建日程。

**对易记的影响：**

日程创建不是易记的最佳突破口。专业日历产品在视图、时区、重复日程、日历同步等方面更成熟。

**易记的差异化机会：**

易记不必做完整日历视图，也不必替代用户现有日历。MVP 阶段只需要把“带未来时间的记录”识别为提醒，必要时后续同步到 Apple Calendar 或 Apple Reminders。

---

#### 12.2.5 Google Gemini / AI 助手类产品

Google Gemini 已支持通过自然语言创建和管理 Google Calendar 事件。AI 助手正在进入日历、邮件、文档、任务等生产力场景。

**对易记的影响：**

长期看，系统级 AI 助手会越来越强，通用型“帮我记一下”的能力可能被大平台覆盖。

**易记的差异化机会：**

大平台 AI 助手通常更强于办公生态和通用任务，但对中文家庭生活语境、物品位置、证件材料、家庭成员共享等垂直场景未必足够细。易记可以先做窄场景、深体验，形成具体用户价值。

---

#### 12.2.6 flomo / Notion / AI 笔记类产品

flomo 强调快速记录和回顾，Notion AI Meeting Notes 等产品强调会议转写、总结和行动项生成。这类产品证明“快速记录 + 后续整理/检索”是一个持续存在的需求。

**对易记的影响：**

笔记类产品已经很多，易记不能只做普通备忘录。

**易记的差异化机会：**

易记应该避免长文笔记和知识管理，专注“生活事实记录”。例如物品位置、证件材料、家庭事务、重要小事。这些记录不需要复杂排版，但需要未来能准确找回。

### 12.3 竞品对比

### 12.4 目标用户分析

#### 12.4.1 第一批目标用户

| 用户类型 | 典型痛点 | 使用场景 |
|---|---|---|
| 家庭事务管理者 | 家里证件、票据、药品、材料很多，容易忘 | 记录户口本、发票、疫苗本、钥匙等位置 |

| 自由职业者 / 小老板 | 客户资料、票据、合同、收款信息分散 | 记录文件位置、合同状态、客户事项 |

| 整理收纳需求强的人 | 家中物品分类多 | 记录收纳箱、抽屉、柜子中的物品 |

| 专业日程管理用户 | 更适合 Fantastical、Google Calendar 等成熟日历 |
| 纯会议记录用户 | Notion AI、飞书妙记等更强 |

### 12.5 需求真实性分析

该项目需求是真实存在的，原因包括：

1. **低频但重要的信息容易遗忘**  
   例如户口本、房产证、备用钥匙、发票、保修卡、药品、合同等。这些信息平时很少用，但一旦需要，找不到会造成明显焦虑。

2. **传统工具记录成本高**  
   用户不愿意为了“户口本放在红抽屉最上面”专门打开笔记、创建分类、输入标题、选择标签。

3. **自然语言非常适合该场景**  
   用户只需要说一句话，不需要理解软件结构。

4. **查询场景明确**  
   用户未来会用非常自然的问题查询，例如“户口本在哪”“上次发票放哪了”“那份合同我记过吗”。

5. **记录本身具有长期价值**  
   这类记录不是一次性任务，可能一年后、两年后仍然有价值。

### 12.6 可行性分析

#### 12.6.1 技术可行性

MVP 技术可行，且不需要一开始接入大模型。

| 能力 | MVP 实现方式 | 可行性 |
|---|---|---|
| 语音转文字 | iOS Speech Framework | 高 |
| 物品位置解析 | 正则 + 关键词 | 高 |
| 日期时间识别 | 简单规则 / 日期解析库 | 中高 |
| 历史查询 | SQL LIKE / FULLTEXT | 高 |
| 模板化回答 | 后端字符串模板 | 高 |
| 提醒通知 | iOS 本地通知 / APNs | 中 |
| 账号同步 | 后端用户系统 | 中 |
| 模糊语义查询 | 后期接向量搜索或大模型 | 中 |

MVP 阶段最重要的是把常见句式做好：

```text
我把【物品】放在【位置】
【物品】在【位置】
【物品】收在【位置】
提醒我【时间】【事项】
```

只要这些句式准确率足够高，就能验证核心需求。

---

#### 12.6.2 成本可行性

在已有腾讯云 Web 服务器的前提下，MVP 新增成本较低。主要固定成本是 Apple Developer Program 年费、域名和可能的数据库费用。

早期可以采用：

```text
iOS 本地语音识别
+
腾讯云 Web 服务器
+
自建 MySQL
+
规则解析
+
关键词搜索
```

该方案不依赖付费模型，不需要 GPU 服务器，适合低成本试错。

---

#### 12.6.3 产品可行性

产品可行，但必须控制范围。早期不应追求“大而全”，而应重点验证：

1. 用户是否愿意每天用它记录小事。
2. 用户是否能在未来真实找回有价值信息。
3. 用户是否信任系统记录的内容。
4. 用户是否认为它比备忘录、微信收藏、相册、系统提醒更方便。

如果这四点无法验证，即使功能很多也没有意义。

### 12.7 主要风险

#### 12.7.1 系统级产品替代风险

Apple、Google 等系统级产品会持续增强语音助手、提醒、日历和 AI 记忆能力。易记如果只做“语音提醒”，容易被替代。

**应对策略：**

聚焦“个人生活记忆库”，尤其是物品位置、证件材料、家庭事务等垂直场景。

---

#### 12.7.2 用户习惯风险

记录类产品最大难点是让用户持续记录。如果用户没有形成习惯，数据库就没有价值。

**应对策略：**

MVP 必须做到极低记录成本：

- 打开快
- 录入快
- 保存快
- 不强迫分类
- 不强迫编辑
- 查询结果可信

---

#### 12.7.3 查询不准风险

如果用户一年后查询“户口本在哪”，系统找不到或返回错误，会严重影响信任。

**应对策略：**

- 保存原始文本，不只保存结构化字段。
- 查询时同时搜索 object_name、location、content。
- 返回结果时说明“你在某日期记录过”，避免假装确定。
- 多条结果按时间倒序列出，让用户判断。

---

#### 12.7.4 隐私风险

用户可能记录证件、家庭、财务、医疗等敏感信息。

**应对策略：**

- 默认不保存原始语音文件。
- 全程 HTTPS。
- 数据库不暴露公网。
- 支持删除记录。
- 后续支持敏感字段加密。
- 隐私政策明确说明数据用途。

---

#### 12.7.5 解析能力不足风险

纯规则解析无法覆盖所有自然语言表达。

**应对策略：**

MVP 先覆盖高频句式，复杂语句保留原文。后续再逐步加入：

- 同义词表
- 用户自定义位置词典
- 向量搜索
- 大模型兜底解析

---

### 12.8 差异化定位建议

建议易记的产品定位是：

> 一句话记录生活细节，未来帮你找回。

可以围绕以下关键词塑造产品心智：

- 生活记忆
- 物品位置
- 家庭资料
- 证件材料
- 长期找回
- 一句话记录
- 低频重要信息

不建议主打：

- AI 助手
- 日历管理
- GTD
- 项目管理
- 会议纪要
- 知识库
- 第二大脑

因为这些方向已有大量成熟产品，且用户迁移成本高。

### 12.9 MVP 验证指标

建议用 20～50 名内测用户验证 2～4 周，重点看以下指标：

| 指标 | 目标值 | 说明 |
|---|---:|---|
| 日均记录次数 | ≥ 2 次/人/天 | 判断是否形成使用习惯 |
| 记录成功率 | ≥ 90% | 用户说完能成功保存 |
| 常见句式解析准确率 | ≥ 80% | 物品和位置提取准确 |
| 明确关键词查询命中率 | ≥ 90% | 如“户口本”“钥匙”“发票” |
| 7 日留存 | ≥ 30% | 初步判断是否有持续价值 |
| 真实找回案例 | ≥ 5 个 | 用户真的靠它找回东西或信息 |
| 用户主动打开率 | 持续增长 | 判断是否有记忆依赖 |

其中最重要的不是下载量，而是：

> 用户是否真的因为易记找回了某个遗忘信息。

这是该产品能否成立的核心证据。

### 12.10 产品经理结论

从市场角度看，易记所处的大方向是成熟市场，提醒、待办、笔记、日历、AI 助手都已经有强竞品。因此，如果做成普通提醒 APP 或普通笔记 APP，成功概率不高。

但从具体场景看，“低频重要生活信息的长期找回”仍然有机会。这个场景足够真实，也没有被主流效率工具充分解决。

因此，本项目的客观判断是：

```text
方向可行，但必须聚焦。
技术可行，但早期不宜复杂。
成本可控，但需要验证留存。
竞争较强，但垂直场景有差异化空间。
```

MVP 最应该验证的不是 AI 能力，而是用户是否认可这个核心价值：

> 我说一句，它帮我记住；很久以后，我问一句，它帮我找回。

如果这一点成立，再逐步扩展提醒、AI 语义搜索、图片记录、家庭共享等功能。

## 13. iOS 本地能力确认

本项目建议采用“本地优先 + 可选联网同步”的方案。经确认，MVP 所需的大部分核心能力均可由 iOS 原生能力支持，不需要一开始依赖服务器或付费 AI 模型。

### 13.1 总体结论

| 功能 | 是否可由 iOS 本地支持 | 推荐技术 | 备注 |
|---|---:|---|---|
| 语音转文字 | 支持 | Speech Framework / SFSpeechRecognizer | 需要用户授权麦克风和语音识别 |
| 文字输入 | 支持 | SwiftUI TextField / TextEditor | 原生支持 |
| 本地数据存储 | 支持 | Core Data / SQLite / SwiftData | MVP 推荐 Core Data 或 SQLite |
| 本地关键词搜索 | 支持 | SQLite LIKE / FTS | MVP 可先用 LIKE，后续升级全文搜索 |
| 本地提醒 | 支持 | UserNotifications | 可用本地通知，无需服务器 |
| 权限管理 | 支持 | iOS Privacy Permissions | 麦克风、语音识别、通知权限 |
| 敏感信息安全存储 | 支持 | Keychain / Data Protection | Keychain 适合保存 token、密钥等小型敏感数据 |
| 云同步 | 支持，但属于可选 | CloudKit / 腾讯云 API | 建议后续再做 |
| 复杂语义理解 | 原生不充分 | 后续接云端 AI / 向量搜索 | MVP 不依赖 |

结论：

> 易记 MVP 的核心闭环——语音输入、文本确认、本地保存、本地查询、本地提醒——可以在 iPhone 端完成。

腾讯云服务器在第一版中不应承担核心可用性，而应作为后续的备份、同步、账号和 AI 增强服务。

### 13.2 语音转文字能力确认

iOS 提供 Speech Framework，用于识别实时音频或录音中的语音内容。项目可使用 `SFSpeechRecognizer` 实现中文语音转文字。

#### 可支持能力

- 实时语音识别
- 录音文件识别
- 指定中文语言环境，例如 `zh-CN`
- 返回识别文本
- 用户确认后保存

#### 注意事项

1. 必须在 `Info.plist` 中声明语音识别用途。
2. 必须请求语音识别权限。
3. 必须请求麦克风权限。
4. 语音识别可用性可能受系统、语言、设备、网络和用户设置影响。
5. MVP 应提供“手动文字输入”作为兜底方案。

#### 推荐设计

```text
用户点击语音按钮
  ↓
请求麦克风和语音识别权限
  ↓
开始录音并实时转文字
  ↓
用户确认识别结果
  ↓
保存到本地数据库
```

#### Swift 示例

```swift
import Speech
import AVFoundation

let speechRecognizer = SFSpeechRecognizer(locale: Locale(identifier: "zh-CN"))

SFSpeechRecognizer.requestAuthorization { status in
    switch status {
    case .authorized:
        print("用户已授权语音识别")
    case .denied, .restricted, .notDetermined:
        print("无法使用语音识别")
    @unknown default:
        print("未知状态")
    }
}
```

### 13.3 本地数据存储能力确认

iOS 支持多种本地持久化方案。Apple 官方 Core Data 可用于保存 App 的永久数据、离线数据和缓存数据。

当前 MVP 实现中，除记录与提醒外，最近搜索历史也应一并持久化，并随本地 JSON 备份导出和导入，避免用户重装或换机后丢失搜索习惯。

#### 可选方案对比

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| Core Data | Apple 原生、稳定、适合对象关系数据 | 学习成本略高 | iOS 单端优先推荐 |
| SQLite | 结构清晰、可控性强、后续跨平台方便 | 需要自己封装 DAO | 推荐给偏后端思维团队 |
| SwiftData | SwiftUI 结合自然、代码简洁 | 较新，兼容性取决于最低 iOS 版本 | 如果只支持较新 iOS 可考虑 |
| UserDefaults | 简单 | 不适合大量记录 | 不建议用于核心数据 |
| Keychain | 安全 | 不适合保存大量记录正文 | 仅用于 token、密钥等 |

#### MVP 推荐

如果项目只做 iOS，推荐：

```text
Core Data
```

如果未来计划支持 Android / Web，并希望数据结构更通用，推荐：

```text
SQLite
```

#### 本地记录模型建议

```text
Record
- id
- content
- objectName
- location
- recordTime
- type
- tags
- source
- createdAt
- updatedAt
- syncStatus
```

### 13.4 本地搜索能力确认

MVP 查询场景主要是明确关键词，例如：

- 户口本在哪？
- 钥匙放哪了？
- 发票在哪里？
- 身份证复印件在哪里？

这些场景不需要一开始使用大模型，本地关键词搜索即可支持。

#### MVP 搜索方案

```sql
SELECT *
FROM records
WHERE content LIKE '%户口本%'
   OR object_name LIKE '%户口本%'
   OR location LIKE '%户口本%'
ORDER BY record_time DESC
LIMIT 5;
```

#### 后续升级方案

| 阶段 | 搜索方式 |
|---|---|
| MVP | SQLite LIKE / Core Data Predicate |
| V1 | SQLite FTS 全文搜索 |
| V2 | 本地同义词词典 |
| V3 | 云端向量搜索 / AI 模糊查询 |

#### 注意事项

中文搜索如果只用 `LIKE`，明确关键词场景足够，但不适合复杂同义表达。例如：

```text
“那个证件在哪”
“办房子的材料放哪里了”
“上次用的那个红本本在哪”
```

这类查询适合后续接入云端语义搜索。

### 13.5 本地提醒能力确认

iOS 的 UserNotifications Framework 支持本地通知。App 可以创建通知内容，并设置触发条件，例如某个具体时间或位置。

#### 可支持能力

- 指定时间提醒
- 每天/每周/每月重复提醒
- 通知标题、内容、声音、角标
- 用户授权后展示本地通知
- 不依赖服务器

#### 推荐用途

MVP 阶段建议使用本地通知处理简单提醒，例如：

```text
明天下午三点提醒我交物业费
```

解析后在本地创建通知：

```text
title: 易记提醒
body: 交物业费
trigger: 2026-06-06 15:00
```

#### 注意事项

1. 必须请求通知权限。
2. 用户关闭通知权限后，App 无法弹出提醒。
3. 本地通知适合单设备提醒。
4. 多设备同步提醒、服务端补偿提醒，后续再接入腾讯云和 APNs。

### 13.6 安全与隐私能力确认

易记会记录生活细节，可能包含证件、家庭、财务、医疗等敏感信息。iOS 本地方案在隐私上更稳妥。

#### 推荐做法

| 数据类型 | 推荐存储 |
|---|---|
| 普通记录正文 | Core Data / SQLite |
| 登录 token | Keychain |
| 云同步密钥 | Keychain |
| 用户设置 | UserDefaults |
| 本地数据库文件 | 使用 iOS 沙盒 + 数据保护 |
| 高敏感字段 | 后续考虑加密后再存储 |

Keychain Services 适合安全保存小型敏感数据，例如密码、token、密钥等，不适合保存大量文本记录正文。

腾讯云服务器在 MVP 中仍然有价值，但不建议作为核心依赖。

#### 第一版可以不强依赖云端

| 家庭共享 | 后续 |

### 13.8 推荐最终技术方案

MVP 建议采用以下端侧方案：

```text
Swift + SwiftUI
  ↓
Speech Framework 语音转文字
  ↓
本地规则解析
  ↓
Core Data / SQLite 本地保存
  ↓
本地关键词搜索
  ↓
UserNotifications 本地提醒
  ↓

```

对应产品策略：

> 没网也能记，没网也能查；联网只是备份和增强。

### 13.9 不建议完全本地实现的能力

以下能力不建议 MVP 阶段强行完全本地实现：

| 能力 | 原因 | 建议 |
|---|---|---|
| 复杂中文语义理解 | 规则难覆盖，原生 NLP 不够专门 | 后续接云端大模型 |
| 模糊查询 | 需要向量搜索或语义模型 | 后续云端增强 |
| 图片识别物品 | 本地可做但开发成本较高 | V2 再考虑 |
| 多设备实时同步 | 冲突处理复杂 | 先做手动备份或单向同步 |
| 家庭共享 | 涉及权限和账号体系 | 后续版本 |
| 端侧大模型 | 包体、性能、耗电、适配复杂 | 不建议 MVP 做 |

### 13.10 产品经理结论

从 iOS 原生能力来看，易记 MVP 可以成立。

最稳妥的实现方式是：

```text
核心功能全部本地可用：
语音转文字、本地记录、本地搜索、本地提醒。

联网能力作为可选增强：
云备份、换机恢复、多设备同步、AI 模糊查询。
```

这样可以同时满足：

- 稳定性：没有网络也能使用。
- 隐私性：敏感生活记录不强制上传。
- 成本控制：服务器压力小。
- 可扩展性：后续仍可接入腾讯云和 AI 能力。

因此，易记第一版建议明确采用：

> iOS 本地优先架构，而不是纯联网架构。

## 14. 到期提醒功能设计

到期提醒是易记 MVP 中建议保留的核心辅助功能之一。它不是产品的唯一卖点，但可以增强“记得住、找得到、到点提醒”的完整体验。

MVP 阶段建议优先采用 **iOS 本地通知** 实现到期提醒，不强依赖服务器。这样即使用户没有网络，也可以收到提醒。

### 14.1 功能定位

到期提醒主要解决以下场景：

| 场景 | 用户输入示例 | 系统行为 |
|---|---|---|
| 一次性提醒 | 明天下午三点提醒我交物业费 | 创建本地提醒 |
| 到期事项 | 6 月 30 日前提醒我续身份证 | 创建到期前提醒 |
| 账单提醒 | 每月 5 号提醒我还信用卡 | 创建重复提醒 |
| 证件提醒 | 护照 2028 年 8 月到期，提前一个月提醒我 | 创建长期到期提醒 |
| 材料提交 | 下周五提醒我交孩子报名材料 | 创建指定日期提醒 |
| 生活事项 | 晚上 8 点提醒我把药放进冰箱 | 创建指定时间提醒 |

产品定位上，到期提醒不是要替代专业日历或任务管理工具，而是服务于“生活记忆”中的时间敏感事项。

| 每年重复提醒 | 可选 | 例如“每年提醒我体检” |
| 农历提醒 | 暂不支持 | 后续版本考虑 |
| 多设备同步提醒 | 暂不支持 | 后续云同步版本实现 |
| 服务端补偿提醒 | 暂不支持 | 后续使用腾讯云 + APNs 实现 |

### 14.4 本地通知实现方案

MVP 阶段使用 iOS `UserNotifications` 实现本地提醒。

#### 实现流程

```text
用户输入一句话
  ↓
本地语音转文字
  ↓
本地规则解析
  ↓
识别为提醒事项
  ↓
保存 records 记录
  ↓
保存 reminders 记录
  ↓
调用 UserNotifications 创建本地通知
  ↓
到期后 iOS 系统弹出提醒
```

#### 本地通知内容建议

```text
标题：易记提醒
内容：交物业费
时间：2026-06-06 15:00
关联记录：明天下午三点提醒我交物业费
```

#### Swift 示例

```swift
import UserNotifications

func scheduleLocalReminder(title: String, body: String, date: Date, identifier: String) {
    let content = UNMutableNotificationContent()
    content.title = title
    content.body = body
    content.sound = .default

    let triggerDate = Calendar.current.dateComponents(
        [.year, .month, .day, .hour, .minute],
        from: date
    )

    let trigger = UNCalendarNotificationTrigger(dateMatching: triggerDate, repeats: false)

    let request = UNNotificationRequest(
        identifier: identifier,
        content: content,
        trigger: trigger
    )

    UNUserNotificationCenter.current().add(request) { error in
        if let error = error {
            print("创建提醒失败: \(error)")
        }
    }
}
```

#### 请求通知权限

```swift
UNUserNotificationCenter.current().requestAuthorization(options: [.alert, .sound, .badge]) { granted, error in
    if granted {
        print("用户已授权通知")
    } else {
        print("用户未授权通知")
    }
}
```

### 14.5 本地数据库设计补充

到期提醒建议单独使用 `reminders` 表或本地实体，不要只存在 `records` 表里。这样方便后续管理、取消、修改和同步。

#### reminders 表 / 本地实体建议

```sql
CREATE TABLE reminders (
  id TEXT PRIMARY KEY,
  record_id TEXT,
  title TEXT NOT NULL,
  body TEXT,
  remind_time DATETIME NOT NULL,
  repeat_rule TEXT DEFAULT 'none',
  advance_minutes INTEGER DEFAULT 0,
  status TEXT DEFAULT 'pending',
  notification_identifier TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

#### 字段说明

| 字段 | 说明 |
|---|---|
| id | 本地提醒 ID |
| record_id | 关联的生活记忆记录 |
| title | 提醒标题 |
| body | 提醒内容 |
| remind_time | 实际提醒时间 |
| repeat_rule | 重复规则：none/daily/weekly/monthly/yearly |
| advance_minutes | 提前提醒分钟数 |
| status | pending/done/cancelled/failed |
| notification_identifier | iOS 本地通知标识 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

### 14.6 到期提醒与生活记忆的关系

易记中的提醒应该与原始记录绑定，而不是孤立存在。

例如用户说：

```text
护照 2028 年 8 月到期，提前一个月提醒我。
```

系统应保存两类信息：

#### records 记录

```json
{
  "content": "护照 2028 年 8 月到期，提前一个月提醒我",
  "object_name": "护照",
  "type": "证件",
  "record_time": "2026-06-05"
}
```

#### reminders 记录

```json
{
  "title": "护照到期",
  "remind_time": "2028-07-01 09:00:00",
  "advance_minutes": 43200,
  "repeat_rule": "none"
}
```

这样未来用户既可以问：

```text
我的护照什么时候到期？
```

也可以收到：

```text
易记提醒：护照快到期了。
```

### 14.8 边界情况处理

| 问题 | 处理方式 |
|---|---|
| 用户没有授权通知 | 保存记录，但提示“通知权限未开启，无法弹出提醒” |
| 时间表达不明确 | 让用户确认，例如“你是指明天上午 9 点吗？” |
| 只有日期没有时间 | 默认上午 9 点提醒 |
| 用户说“月底前” | 默认当月最后一天上午 9 点，并允许修改 |
| 用户说“提前一天”但没有到期日 | 仅保存记录，不创建提醒，提示需要到期时间 |
| 通知创建失败 | 标记 reminder.status = failed |
| 用户删除记录 | 同步删除或取消关联提醒 |
| 用户修改提醒时间 | 取消旧通知，创建新通知 |
| App 被卸载 | 本地提醒和本地数据都会丢失，后续可通过云备份解决 |

### 14.9 后续云端提醒扩展

MVP 阶段使用本地通知即可。后续如果做云同步和多设备提醒，可以扩展为：

```text
iOS 本地提醒
  +
腾讯云 reminders 表
  +
定时任务扫描
  +
APNs 推送
```

云端提醒适合解决：

- 换机后恢复提醒
- 多设备同步提醒
- 家庭共享提醒
- 服务端补偿通知
- 重要提醒二次通知

但云端提醒会增加复杂度，包括账号体系、设备 token、APNs 证书、定时任务、失败重试等，不建议 MVP 第一版强依赖。

### 14.10 产品经理结论

到期提醒应作为 MVP 的明确功能，但实现方式建议从简单开始：

```text
第一版：
iOS 本地通知
+
一次性提醒
+
简单重复提醒
+
本地提醒列表

后续版本：
云同步提醒
+
多设备提醒
+
AI 自动识别到期事项
+
重要事项二次提醒
```

这样既能满足用户“到点别忘”的基础需求，又不会让早期架构变得过重。

#### iOS MVP 手动回归清单

1. 首次安装后进入录入页，确认语音权限、麦克风权限和通知权限提示链路正常。
2. 拒绝语音权限后，确认录入页会显示错误提示，并可直接跳转系统设置。
3. 使用文字录入一条“物品位置”记录，保存后确认会自动回到首页，并高亮刚保存的记录。
4. 使用语音录入一条提醒记录，确认提醒能保存，并在授权通知后进入系统通知。
5. 将本地记录补到 `30` 条，确认第 `31` 条会被拦截，且提示文案正确。
6. 在首页、搜索页和提醒页分别进入记录详情，删除记录后确认详情页和列表不会残留旧内容。
7. 导出 JSON 备份后重新导入，确认记录、提醒和最近搜索历史都能恢复。
8. 选择一个空文件、无效 JSON 文件或非易记导出的 JSON 文件，确认导入失败提示为可理解文案。
9. 关闭通知权限后修改提醒，确认提醒仍可保存到本地，但状态说明明确提示不会进入系统通知。
10. 真机锁屏等待测试通知，确认 10 秒测试通知和普通提醒通知都能送达。

5. 部署 API 服务。
6. 配置 Nginx 反向代理。
7. 绑定域名。
8. 配置 HTTPS。
9. 配置防火墙和安全组。
10. 设置数据库定期备份。

### 17.4 后续安全建议

- 所有接口必须使用 HTTPS。
- 用户 ID 不要完全依赖客户端传入，后期应加入登录态。
- 数据库密码不要写死在代码中。
- 使用 `.env` 管理环境变量。
- 定期备份数据库。
- 敏感记录后续可考虑字段级加密。
- 服务器只开放必要端口，例如 80、443、SSH。

## 18. 隐私与安全

该产品会记录用户的生活细节，可能涉及证件、家庭、财务等敏感信息，因此隐私设计非常重要。

### 15.1 MVP 阶段必须做到

- 使用 HTTPS 传输。
- 数据库限制公网访问。
- 不明文保存用户密码。
- 后台管理入口需要鉴权。
- 隐私政策中说明数据用途。
- 支持用户删除记录。

### 15.2 后续建议

- 对敏感字段加密存储。
- 支持本地优先存储。
- 支持导出个人数据。
- 支持完全删除账号。
- 不默认上传原始语音文件。
- 用户可选择是否保存语音原文件。

## 21. 总结

易记 MVP 的核心不是做一个复杂的 AI 助手，而是先解决一个非常具体的问题：

> 用户把东西放在哪里、什么时候做过什么事，未来还能可靠找回来。

早期最低成本方案建议采用：

```text
iOS 原生语音识别
  +
腾讯云 Web 服务器
  +
规则解析
  +
MySQL / PostgreSQL
  +
关键词查询
  +
模板化回答
```

这个方案开发成本低、上线速度快、服务器压力小，适合先验证真实需求。

当 MVP 证明用户确实愿意持续记录和查询后，再逐步扩展 AI 语义理解、向量搜索、图片识别、自动提醒和家庭共享等高级能力。
